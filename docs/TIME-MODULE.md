# 时间模块（Time）设计草案

> 状态：**设计待确认**，不是实现说明。写于 2026-11-03。
> 目标：把"节律"做成一个正式插件，一次做完，不做小补丁。

## 1. 它是什么

时间模块是**会话之外唯一能主动让会话开始说话的东西**，也是**唯一提供系统时间的地方**。

它同时是：

- 日程表（什么时候醒、什么时候睡、什么时候做例行的事）
- 时钟（`now()` 的唯一来源）
- 守门人（谁能打断当前 Focus、谁要排队）
- 外部控制的入口（脚本给会话设计时器、暂停、恢复）

它**不是**：消息总线、记忆系统、模型调度器。

## 2. 边界（明确不做什么）

| 不做 | 由谁做 |
|---|---|
| 强制终止正在生成的回合 | 核心/DSH 没有这个能力；只能软终止 |
| 跨 Focus 的全局注意力积压 | 核心的 `focus`/`delivery`；时间模块只管"日程视角"的队列 |
| 记忆整理本身 | `dream` 插件；时间模块只负责"叫它起床" |
| 对外部应用发消息（QQ/B站） | 各自适配插件 |
| 生成人格内容 | `persona` 插件；时间模块只注入"现在是睡觉时间"这类状态 |

## 3. 核心概念

### 3.1 阶段（phase）

会话任意时刻处于一个阶段：

```
awake    醒着，可以说话、用工具
sleeping 睡觉，人格被注入"你在睡"，只有 sleeping 日程相关的事允许穿透
paused   暂停，不安排任何唤醒；已排队的东西保留
```

阶段由日程驱动，也可以被外部 API 强制切换。

### 3.2 日程（schedule）

一条日程 = 一个时间点 + 一个动作：

```json
{
  "id": "night",
  "kind": "sleep",          // wake | sleep | routine | timer
  "at": "23:00",            // HH:mm（每天）或 ISO 时间点（一次性）
  "durationMin": 480,       // sleep 用：睡多久
  "message": "该睡了",       // 触发时发给会话的第一句话
  "pierce": { "qq": "mention", "*": "never" }
}
```

- `sleep` 是特殊日程：进入 `sleeping` 阶段、调用 `dream`（如果存在）、并在醒来时切回 `awake`
- `wake` 是一次性或多个固定点
- `routine` 是"到点提醒她做某事"，不改变阶段
- `timer` 是外部脚本设的一次性定时器（等价于 routine，但带来源标记）

### 3.3 消息穿透

所有想"让会话说点什么"的插件，**不直接 push 会话**，而是提交给时间模块：

```js
time.offer({
  from: 'qq',                 // 来源标签
  text: '群里有人 @ 你',
  focus: 'qq:group-123',      // 想进入的 Focus（可选）
  pierce: 'mention',          // 这次消息的穿透级别
  priority: 5,
})
```

时间模块的判定：

```
阶段是 paused        → 一律排队
阶段是 sleeping      → 只有 level=always 且与睡眠日程声明相符的才放行
阶段是 awake 且无 Focus → 放行
阶段是 awake 有 Focus   → 调 focus.canPierce(from, {mention}) 决定
放行 → 交给 delivery；不放行 → 进时间模块自己的队列
```

**注意**：这里的队列是"日程视角"的积压（按阶段/日程/优先级），不是核心维护的跨 Focus 注意力队列。两个东西不合并。

### 3.4 软终止

会话通过模型主动调用工具来"结束这一轮"：

```js
time.end_turn({ reason: '困了' })
```

语义：**这一轮不再追加任何消息**，直到下一日程唤醒。核心没有强制停止能力，时间模块也不假装有。

## 4. 对外工具（模型可调用）

| 工具 | 作用 |
|---|---|
| `time_now` | 现在几点、当前阶段、下一个日程 |
| `time_schedule` | 看今天/明天的日程 |
| `time_end_turn` | 主动结束这一轮（软终止） |
| `time_sleep` | 主动去睡（进入 sleeping，可带时长） |
| `time_wake` | 主动醒来 |

外部脚本用**服务 API**（不是工具）：

```js
time.armTimer({ at, text, focus, pierce })   // 设计时器
time.cancel(id)
time.pause() / time.resume()
time.status()
time.forceSleep({ durationMin })
time.forceWake()
```

## 5. 与 dream 的关系（轻依赖）

```
sleep 日程触发
  → time 进入 sleeping
  → time 广播 onSleep（不 await）
  → dream 自己订阅 onSleep → 跑整理（幂等，alreadyRan 兜底）
  → 醒来时 time 广播 onWake
```

时间模块**不认识** dream 的内部 job；dream 不依赖 time 存在（没有 time 时用 `isDue` 自己判断）。两边只通过 `onSleep/onWake` 事件耦合。

## 6. 与 focus 的关系（不能删）

- `sleeping` 阶段，时间模块自己持有一个 Focus：`label: 'sleep'`
- 其它来源要穿透，走 §3.3 的判定
- 醒来时释放该 Focus
- 因此 **focus 不能删**；P2 里"二选一"的结论是：**接进来，不删**

## 7. 时钟的唯一来源

- `time.now()` 是唯一系统时间入口
- 其它插件不得自己 `Date.now()` 决定"现在是什么时候"（测试/日志可以）
- 实现上：host 的 `ctx.now` 由时间模块注册后接管；时间模块未启用时回落到系统时钟
- 这是硬约定，写进边界测试

## 8. 状态与持久化

```json
{
  "phase": "awake",
  "since": 1793...,
  "lastSchedule": "night@2026-11-02",
  "queue": [ { "from": "qq", "text": "...", "at": 1793..., "priority": 5 } ],
  "timers": [ { "id": "t1", "at": 1793..., "text": "..." } ]
}
```

- 写在 `state/time.json`（不是记忆库）
- 重启后：阶段恢复、队列恢复、过期的一次性定时器补发一次
- 单实例：文件锁，第二个进程只读并拒绝安排日程

## 9. 外部脚本怎么用

现在外部脚本直连会话发通知，以后改为：

```
外部脚本 → 时间模块 API（HTTP 或本地工具） → 时间模块判定 → delivery → 会话
```

一步到位的最小形态：时间模块暴露一个本地 HTTP 入口（或 CLI），支持：

```
POST /timer {at, text, focus}
POST /pause
POST /resume
GET  /status
```

## 10. 失败语义

| 情况 | 行为 |
|---|---|
| 没有会话在跑 | 日程触发后标记 `pendingWake`，会话一挂上就补发 |
| 会话正在生成 | 排队，等这一轮结束（不打断生成） |
| dream 不存在/失败 | 记录日志，不阻塞醒来 |
| 进程在睡觉中途退出 | 重启后按 `lastSchedule` 判断：没到点就继续睡，到点补醒 |
| 排队消息过期 | 超过 TTL 丢弃并计数（可观测） |

## 11. 待你确认的设计点

1. **日程表示**：每天固定时刻（`HH:mm`）+ 一次性时间点，够不够？需要 cron 或"每 N 小时"吗？
2. **睡眠结束条件**：固定时长 / 到下一个日程 / 做梦完成，三种怎么组合？
3. **睡眠时长默认**：8 小时？还是按"醒来日程"反推？
4. **穿透级别**：沿用 focus 的 `always/mention/never` + glob，还是给时间模块单独的语义？
5. **队列持久化**：重启后排队消息要不要保留？保留多久？
6. **外部 API 形态**：本地 HTTP 端口，还是只提供 CLI/工具？
7. **多会话**：时间模块只服务一个会话，还是能同时管多个？（倾向：一个）
8. **时钟接管**：`ctx.now` 由时间模块接管——同意吗？这会影响所有插件。
