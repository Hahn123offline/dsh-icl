# 记忆设计评审：轻量（recent）与长期（blocks）

> 对象：你对"轻量 vs 长期"的口头设计。
> 结论：**方向成立**，而且比现在把 light-memory 单独做成插件更对。
> 但有三处必须先定，否则实现出来的"统一 recall"会变成新的糊状层。

---

## 一、我同意什么

| 你的判断 | 我的评价 |
|---|---|
| 轻记忆对模型不可见，只有统一的 `recall` | 对。模型不该知道自己的记忆分几层，否则它会在语气里暴露"我刚查了缓存" |
| `remember` 一律写"今天"，跨天由梦境沉淀 | 对。写入路径单一，才不会有第二份真相 |

| 命名空间由做梦注册；事件、人物是两大块 | 对。命名空间是"存储契约"，管理策略不属于记忆库 |

| 做梦多轮（事件 / 人物 / 梗） | 对。三种块的管理策略完全不同，不该塞进一条流水线 |

| 世界状态：拿不到就不显示，默认全空 | 对。唯一要补的是"没有"和"坏了"要能区分（见 §8） |

## 二、三处必须先定的地方

### 1. `recall` 的"不重复"必须由游标保证，不能靠服务端猜

你说"再次 recall 取下一批，不重复记起当前的东西"。这句话有两种实现：

- **服务端记住"这一轮已经给过什么"** → 换会话、进程重启、模型并行调用都会错乱
- **返回一个不透明游标**（`cursor`），下次带上 → 无状态、可重放、可测试

建议后者：

```js
recall({ kind: 'event', limit: 5 })
→ { items: [...], cursor: 'c1', more: true }

recall({ kind: 'event', limit: 5, cursor: 'c1' })
→ { items: [...], cursor: 'c2' }
```

游标里只放"排序键 + 已给过的 id"，不放业务。服务端另有一份**短期去重**（同一回合内已返回的块不再重复），但那是优化，不是正确性来源。

### 2. 两类东西混合返回时，必须解耦"形状"

`recall` 要同时给"今天的随手记"和"长期块"，但两者形状不同（一个是一句话，一个是"摘要+正文"）。
如果直接拼成一段文字，模型会分不清哪条是"我刚记的"、哪条是"梦里沉淀的"。
建议统一成**一种条目**，带来源标签：

```
[今天] 他说周末可能去看海
[事件 · 3 天前] 去看海的约定被推迟
[人物 · 阿伟] 怕水，但想去海边
```

标签由 `recall` 生成，模型不需要知道底层是哪个命名空间。

### 3. "昨天原文保留但不可 recall"要在存储层强制

现在 `memory.query` 是通用接口，任何插件都能查到昨天的 `recent:*`。
如果只靠 `recall` 自己过滤，迟早会有插件绕过去（今天已经踩过"两条通道各送一遍"的坑）。

建议：**命名空间注册时就声明 `recallable`**，`memory.search` 默认只搜 `recallable:true` 的命名空间，
查历史原文必须显式 `includeArchive: true`（只有做梦/管理插件会用）。

## 三、职责切成三层（替代现在的 light-memory 插件）

| 层 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 存储 | `memory`（已有） | 命名空间注册、读写、检索原语 | 不懂"事件/人物/梗"，不懂权重曲线 |
| 回忆 | **新插件 `recall`** | 统一的 `remember` / `recall`；合并 recent + blocks；生成标签与游标 | 不做沉淀，不改块 |
| 沉淀 | **`dream`** | 多轮任务：事件块、人物块、梗词；高权重引用今天的随手记 | 不做回忆排序 |

原来的 `light-memory` 插件消失：它的 `remember` 并入 `recall`，它提供的能力并进"今天的 recent 命名空间"。
这样模型侧只有两个工具（`remember` / `recall`），和你的描述一致。

## 四、命名空间契约（记忆库只认这个）

```js
memory.registerNamespace({
  id: 'event',
  label: '事件',
  schema: 1,
  recallable: true,          // 能不能被 recall 检索
  weighable: true,           // 有没有权重/遗忘
  retention: 'forever',      // 或 'days:30'
  halfLifeDays: 30,          // 仅 weighable
  keyPattern: '^evt:',
})
```

- **注册者**：做梦插件在启用时注册 `event` / `person` / `slang`；主会话的 `recent:<session>` 由 `recall` 插件注册
- **内容不归注册者独有**：注册完以后任何插件都能读写（你说的"命名空间不属于做梦"），
  只有 schema 与保留策略归注册者
- 记忆库只校验"命名空间存在 + key 不重复 + 大小上限"，**不解释内容**

## 五、块格式草案（待你拍板）

### 事件块（`event`）

```json
{
  "key": "evt:2026-11-01:3",
  "text": "一行脱敏摘要",
  "data": {
    "body": "正文（第一人称，保留细节）",
    "day": "2026-11-01",
    "sources": ["recent:abc#12", "recent:abc#15"],
    "people": ["3429502459"],
    "tags": ["约定", "看海"]
  },
  "weight": 1.0
}
```

- `sources` 是**幂等与追溯**的关键：重跑做梦时能知道哪些随手记已经被消化过
- `people` 用 QQ 号，不用昵称（身份只认号码）
- 摘要一行，正文可以长；脱敏在生成时做（人名/号码在正文里可以出现，但摘要不含）

### 人物块（`person`）

```json
{
  "key": "person:3429502459",
  "text": "阿伟：怕水，想去海边",
  "data": {
    "qq": "3429502459",
    "aliases": ["2078446807"],
    "facts": [{ "text": "怕水", "since": "2026-10-20", "weight": 1.4 }],
    "narrative": "第一人称的人物档案正文，整块重写",
    "sources": ["recent:abc#20"]
  }
}
```

- **整块重写**：每次做梦生成新的 `narrative`，旧版留在版本历史里（可回滚）
- `aliases` 是"统一不同账号"：合并必须有证据（同一人亲口说、或明显同一行为），**绝不自动合并**
- 主会话的 `remember(kind='person', qq=…)` 只写 `recent`；做梦时按高权重并入人物块

### 梗/用语块（`slang`）

```json
{
  "key": "slang:难绷",
  "text": "难绷：绷不住了的简写",
  "data": { "usage": "看到离谱事时", "examples": ["难绷，这也行"], "sources": ["recent:abc#31"] }
}
```

## 六、权重与遗忘（可以直接算的那种）

```
score(item) = similarity(query, item) × weight × exp(-ageDays / halfLife)
weight'     = min(maxWeight, weight + boost)
```

- `ageDays` 从 `last_recalled_at`（没被召回过就用 `created_at`）算
- `boost` 只在两种情况给：**首次被 recall 返回**、**被做梦引用进新块**
- 不因为"模型又 recall 了一次"就无限加权重（否则反复 recall 会把它顶到永远第一）
- 每个命名空间声明 `halfLifeDays`：事件 30、人物 180、梗 90（初值，可调）

**需要你定**：boost 该不该在 recall 返回时就给？我倾向"给很小的值"，
真正显著的回权留给做梦（它才是"真的被我再次想起"的证据）。

## 七、做梦的多轮编排

```
dream.run()
  ├─ job events   ：今天的 recent → 事件块（可多条）→ 标 sources 已消化
  ├─ job people   ：今天涉及的人物 → 逐人整块重写
  └─ job slang    ：今天的新词 → 新增/更新梗块
```

要补的三条工程约束：

1. **幂等**：`(day, job)` 记录一次（state 文件或 `dream_runs` 命名空间），重跑不会重复写块
2. **可重跑**：每个 job 独立的输入与输出，失败只重跑那个 job
3. **可中断**：job 之间不共享内存状态，进程重启后能接着跑

每个 job 用自己的提示词（人格化的第一人称），提示词属于 dreaming 插件配置，**不进主会话**。

## 八、世界状态：撤回可以，但要能区分"空"与"坏"

你的设计（默认全空、被动投喂、撤回即消失）我完全同意。补一条：

- 来源返回 `[]` = **它现在没东西可说** → 从树里消失（对）
- 来源抛错/超时 = **它坏了** → 也不该显示假信息，但要在**日志与 detail 层**留痕：
  `read({owner})` 里带 `{stale:true, error}`，brief 层不出现任何"坏的提示"

否则 QQ 插件崩了，世界状态会安静地少一行，没人知道它坏了。

## 九、需要你拍板的问题（按重要性）

1. **`recall` 无参默认是"事件"还是"全部可回忆类别"？**
   你说"默认是事件"；但人物与梗会因此被默认藏起来。我倾向默认全部（带标签），`kind` 用于收窄。
2. **`remember` 要不要分 `kind`？**
   如果要"给人物记一条"，需要一个 `remember({kind:'person', qq, text})` 的入口；否则人物只能靠做梦从普通笔记里推断。
3. **boost 时机**：只在"首次返回"和"做梦引用"，还是每次 recall 都给小 boost？
4. **人物块合并多个 QQ 号的证据标准**：只接受"本人明说"，还是允许"明显同一人"的推断（风险：认错人）？
5. **`recall` 的游标有效期**：跟会话走（重启失效）还是持久化（可跨重启续读）？
6. **事件块粒度**：一天一块，还是"一天多块（按话题）"？这条直接决定向量检索的质量——我倾向按话题切，与你说的"智能切块"一致。

## 十一、已定的决定（2026-11-01，主人拍板）

| 问题 | 决定 |
|---|---|
| recall 无参默认 | **全部可回忆类别，按时间**；混合结果必带标签 |
| remember 分不分 kind | **分**，与长期命名空间一一对应（event / person / slang） |

## 十二、做梦流水线与质量评测（2026-11-01）

### 三个 job（独立、幂等、可重跑）

| job | 读 | 写 | 失败时 |
|---|---|---|---|
| `events` | 今天 `event` 命名空间的 note | 若干 `event` 块（按话题） | note 不标已消化，下次重跑 |
| `people` | 今天 `person` note 按 QQ 分组 | 逐人整块重写 `person:<qq>` | 同上 |
| `slang` | 今天 `slang` note | `slang:<term>` 新增/更新 | 同上 |

幂等标记：`dream-run` 命名空间里的 `run:<day>:<job>`。
已消化标记：note 的 `data.consolidated`。

### 块格式（已实现）

- 事件：`text` = 一行摘要；`data = { body, day, people[], tags[], sources[] }`
- 人物：`key = person:<qq>`；`data = { qq, narrative, facts[], sources[], rewrittenAt }`
- 梗：`key = slang:<term>`；`data = { term, meaning, usage, examples[], sources[] }`

### 质量评测：`tools/dream-eval.mjs`

```
node tools/dream-eval.mjs           # 假模型（不需网络）
node tools/dream-eval.mjs --real    # 真模型（ICL_LLM_BASE / ICL_LLM_MODEL）
node tools/dream-eval.mjs --real --json
```

它量四件事：

1. **结构**：块数量、平均字符数、块与块之间的近似重复率（二元组 Jaccard）
2. **覆盖**：预设的「应该记住的事实」有多少进了块
3. **找回**：探针查询 → `recall` 前 3 条里有没有期望的块（recall@3，**需要嵌入服务**；
   没接嵌入时会如实跳过，不拿字面匹配冒充语义能力）
4. **样例**：打印前几块供人看

阈值：覆盖 < 60%、重复率 > 0.5（或有嵌入时 recall@3 < 60%）→ 退出码非 0。

### 为什么要这么量

- 只看「能不能跑」是不够的：一天一块也能跑，但检索全是泛内容
- 重复率能直接抓「同一件事写了三遍」
- 探针能抓「切得太碎，对不上话题」
- 固定一天的 fixture 能做回归：换模型/改提示词后重跑就知道好坏

## 十三、待做：整理轮（合并与去重）—— 2026-11-01 定义

做梦的第四个阶段，尚未实现，先把约定写下：

- **目标**：把时间相近、逻辑相关、或互相矛盾/重复的块适当合并，
  让长期记忆保持均匀、无杂质；块长度有上限（超长就拆）。
- **矛盾处理**：两个块说法不一致且无法判定时，合并结果写“不确定”，而不是选一个。
- **主会话反馈**：`remember` 新增 `tag: "resolve"`，表示“这件事我其实记错了 / 现在要改”；
  整理轮优先参考这些反馈，再决定合并/改写哪个块。
- **优先级**：整理轮在所有 job 之后跑，幂等标记与其它 job 一致（`run:<day>:cleanup`）。

人物档案的字段已按此预留：

## 十四、整理轮（已实现）—— 2026-11-01

### 顺序：放在最后（events → people → slang → cleanup）

理由：

1. 整理治的是**结果**不是输入——它要看到今天新写出的块，才能把新旧重复一起合并
2. 失败不连带丢失——新记忆已落库，整理失败只是"不够干净"，不会弄丢一天
3. 纠正（resolve）针对的是**最终状态**，换句话说它要能改掉刚写的错块

代价：同一次运行内，重复块会存在几秒钟（没人会在这几秒里 recall）。

### 范围：event / person / slang 都管，但动作不同

| 命名空间 | 整理动作 |
|---|---|
| `event` | 合并同一件事/同一个人的重复块；矛盾且分不清 → `uncertain: true` |
| `person` | **不合并**（一人一块）；只按纠正改写档案正文 |
| `slang` | 合并同义/近义词条 |

### 纠正（resolve）

- 主会话 `remember({kind:'resolve', text})` 写进 `resolve` 命名空间
- 它 **recallable: false**：不会被 recall 检索到，只给整理轮看
- 整理轮必须处理它：按纠正改写对应块，然后把 note 标 `consumed`
- **跨天的未消化纠正也会处理**（纠正可能晚到）——这一点需要你确认

### 安全：合并是软删除

- 被合并的块不物理删除，标 `superseded: true` + `supersededBy`
- `recall` / `memory.search` 过滤掉 `superseded`，但数据还在（可追溯、可回滚）
- 合并结果保留 `mergedFrom`（合并了哪些 key）

### 当前参数

- 每轮每个命名空间最多看 60 块；输出预算 1500 tokens
- 幂等：`run:<day>:cleanup`
- 实测（DeepSeek + bge-m3）：cleanup ok+0（无重复时不动），覆盖 100%、recall@3 100%、重复 0.01

## 十五、碎片（不成块的笔记）去哪了—— 2026-11-01

**原则：不能丢。不够成块不等于没用。**

| 阶段 | 行为 |
|---|---|
| 写入 | `remember` 写进命名空间的 `kind=note`（原文） |
| 做梦时模型不肯成块 | **不标已消化**，记 `deferred`；明天跟新材料一起重试 |
| 每次 recall | 未消化的 note（**任何日期**）都会出现：今天的标 `[今天]`，跨天的标 `[未整理 · MM-DD]` |
| 已消化的 note | 不再以 note 身份出现（它已经变成块） |
| 人物材料不足 | people job 输出空 profile → 不写块、不标已消化，碎片继续可被回忆 |

为什么不单开一个"待办命名空间"：
那会让碎片和它的分类分家，召回时还要再合并一次。
碎片留在**它本来的命名空间**里，靠 `consolidated` 字段区分状态。

### 待完善

- 整理轮目前只看 `kind=block`；将来可以让它把"多条碎片"合并成一个块（碎片磁相关时）
- `deferred` 次数可以用来升级：长期成不了块的碎片，应当降权或归档，而不是永远占着回忆名额

## 十六、整理轮实测（2026-11-01）

工具：`node tools/cleanup-eval.mjs [--real] [--json]`

夹具：两个重复的事件块 + 一个很短的块 + 一个人物档案 + 一条主会话纠正。

真模型（DeepSeek + bge-m3）结果：

```
job: merged 1, rewrites 1, consumed 1
合并后 evt:sea-1：他周末要去看海，并不怕水      ← 纠正被应用
evt:sea-2：已合并（软删除，不再被 recall）
人物档案：他并不怕水                    ← 按纠正改写
小块 evt:short：保留，没有被为了“整齐”合并掉
碎片：仍可被 recall 检索到
向量：1 条（remember 写入的碎片已向量化）
```

### 这次一起改的两件事

1. **碎片也向量化**：`remember` 写入后立即 `memory.index()`。
   以前只有梦境产出的块会向量化，碎片只能靠字面搜到。
2. **整理不追求长度一致**：提示词明确写“不要为了长度差不多而合并；
   小块没有矛盾就原样留着”。目标是去重与消除矛盾。

### 仍然存在的一个小坑

在接上嵌入服务之前已经存在的块不会自动补向量（`cleanup-eval` 里手写的块
就是这种情况）。以后可以在整理轮或梦境里加一步“缺向量的块补建索引”。

## 十七、自动召回与旧版对比（2026-11-01）

### 现在的做法：`eager-recall` 插件

每条用户消息进来时，核心调一次 `prompt.turnText({ message })`：

```
message → memory.search(query=message, minScore, limit)
       → 只取 score ≥ minScore 的前 2 条
       → 拼成 ≤200 字的「你可能记得（检索结果，仅供参考）」
```

三道闸门：阈值、条数 ≤ 2、字数 ≤ 200。可以 `enabled: false` 一行关掉。

**只注入提示词，不发消息**：走 `ctx.prompt.onTurn`（核心统一装配），
不走 `ctx.push`。有测试断言：自动召回之后，投递队列仍为空。

### 与旧版的对比

| | 旧版（focus-core `memory-inject`） | 新版（eager-recall） |
|---|---|---|
| 触发 | 插件每 5s 轮询 `/api/agent/context`，**每轮都注入** | 每条消息异步检索，**够像才注入** |
| 条数 | topK 5 | ≤ 2 |
| 字数 | recallChars 1400 | ≤ 200 |
| 阈值 | minScore 0.55 | 可配，默认 0.55 |
| 统计 | 用 `pending_injection` 避免轮询刷 use_count | 轮询本身不存在，只在真正回忆时 boost |

结论：你的怀疑对了——**旧版自动召回几乎是 100% 每轮触发**，
而手动 `recall` 工具在旧版里几乎没有存在感（模型不会主动查）。
新版把它变成"阈值驱动的小注入"，且保留手动 `recall` 作为精确查询。

### 待评估

- 阈值 0.55 在 bge-m3 上是否合适（需要真实对话调）
- 是否要在工具调用后再补一次（双向），还是保持"只在用户消息时"
- 关了自动召回时，模型是否真的会主动调 `recall`（需要真实测试）

## 二十、人物档案改成"有就写"（2026-11-01）

之前：材料不够三段式 → 不写块。结果五天聊天里一个人物档案都没有。

现在：

- 提示词明确"有几条写几条，但必须能认人"；至少要有称呼/关系 + 一件具体的事
- 目标写法："一个陌生人读完大致能认识 TA"
- 模型硬是给空时，**用笔记原文拼一份薄档案**，不把人丢掉
- 材料不足（笔记 < 3 条或 profile < 60 字）标 `provisional: true`
- 仍然**每天整块重写**（人物 job 读跨天未消化笔记 + 相关事件块）

回放实测（QQ 5 天，真模型）：

```

```
