# 语料层（lexicon）：梗、黑话、说法与风格（设计稿）

> 现状：`slang` 命名空间只是能跑，不是最终形态。
> 本文记录讨论方向，尚未定稿，也未开始改代码。

## 一、它到底是什么

不是"梗库"，更接近**怎么说话的知识**：

| 类型 | 例子 | 来源 |
|---|---|---|
| 词义 | 「难绷」= 绷不住了 | 群聊、B站、网络 |
| 用法 | 这个词只在熟人局用、长辈面前别用 | 场景观察 |
| 内部黑话 | 「大记忆恢复术」= 补录长期记忆 | 本群自造，网上搜不到 |
| 说话风格 | 她最近爱用短句 + 反问 | 长期归纳 |

所以命名建议从 `slang` 换成 `lexicon`（语料），`kind` 只区分 `term`（词）
与 `usage`（用法）。

**已定：style 不在这里。** 说话风格属于人格动态演进，不该由词汇表承载；
模型本身也有上下文学习能力。lexicon 只做词汇层。

## 二、桶（bucket）怎么分

**已定：两个轴都是索引**，查询时任选其一或组合：

- **来源轴**：`conv`（哪个群/私聊）、`platform`（qq / bili / web）
- **主题轴**：`tags`（技术、游戏、校园…）

查询时两者可组合：

```
lexicon({ conv: 'group:1057812765' })       // 这个群的黑话
lexicon({ platform: 'bili' })               // 刷 B 站学到的
lexicon({ tag: '校园' })
```

## 三、字段（草案）

```json
{
  "term": "大记忆恢复术",
  "kind": "term",
  "meaning": "把旧聊天记录补录进长期记忆",
  "usage": "只在群里自嘲时用",
  "scope": { "conv": "group:1057812765", "platform": "qq" },
  "tags": ["内部黑话", "记忆", "校园"],
  "confidence": 0.9,
  "usageState": "active",
  "decay": { "weight": 1.8, "lastSeen": 1793000000000 },
  "origin": {
    "conv": "group:1057812765",
    "messageId": "...",
    "url": null,
    "seenAt": 1793000000000
  },
  "evidence": [{ "type": "note", "id": 12 }]
}
```

**出处统一叫 `origin`**，不分"首次出现"和"资料来源"：
可以是网络链接，也可以是"某群聊某事、什么时候"。

**已定的三个独立维度**：

| 维度 | 含义 | 例子 |
|---|---|---|
| `confidence` | 我对这个说法的确定程度 | 内部黑话 confidence 高，但网上搜不到 |
| `usage` | 现在还在不在用 | `active / fading / retired`——没人说了就别乱接 |
| `decay` | 我还能不能想起来 | 遗忘曲线；很久不出现会变淡 |

"过气"和"遗忘"是两件事：过气是**别人不用了**，遗忘是**我记不清了**。

## 四、维护：做梦单开轮次

1. **采集**：从当天对话里抽候选（新词、反复出现的说法）
2. **求证**：网上搜不到的，进 note 待办（"搜一下这个词"），
   与"明天问问他 xx"同属待办层
3. **归并**：同义合并、过气标记（`freshness: fading`）
4. **跨平台**：B 站/网页学到的也进同一个桶，只是 `scope.platform` 不同

## 五、检索与使用

- 专用工具 `lexicon(...)`：**批量返回**（一次给一簇，不是一条）
- 场景提示：进入某个群时，可提示"这个群的黑话可以用 group:xxx 搜"
- 跨平台：同一个词在不同平台可能有不同用法，按 `scope` 区分

## 六、边界：它不是人格，也不该变成人格

- 语料是**数据**，可以被检索、可以引用；写不写进提示词、怎么写，
  由人格层决定
- 风险：如果把"最近爱用短句"直接注入提示词，等于偷偷改人格
- 建议：语料层只提供"可查的知识"，**不自动注入风格**；
  风格是否外显，留给上线前的仿真契约

## 七、和现有命名空间的关系

| 现有 | 建议 |
|---|---|
| `slang` | 改名/升级为 `lexicon`，旧数据按 `kind: term` 迁入 |
| `event` | 不变（事件） |
| `person` | 不变（人物档案） |
| `note` | 不变（备忘/待办），承接"搜一下这个梗" |

## 八、已定结论

1. **桶**：会话与话题**都是索引**，查询可组合
2. **style 不进来**：那是人格演进，不是词汇表
3. **usage 与 decay 分开**：没人说 ≠ 我忘了；过气不乱接，遗忘慢慢淡
4. **出处统一为 `origin`**：链接或"某群/某事/时间"，不再单列"首次出现"
5. **事实与梗不强行切分**：各自按语义使用；一段事实里可以有梗，
   一个梗也可能带着来源说明，二者不冲突

## 九、还没定的

- 采集轮怎么抽候选（只抽新词？还是也抽"用法变化"？）
- 桶的粒度：一个群一个桶，还是"群 + 主题"再分？
- 跨平台同形不同义怎么区分（同名梗在不同平台意思不同）

## 十、定稿（2026-11-02）

### 采集：两种都抽

- **新词**：第一次出现的说法
- **用法变化**：老词被用在新的场景/人群（同一 term 加一条 origin + usage）

参考旧实现 `dsh-qq/src/slang-learner.js` 的可取之处：

1. **候选 → 确认 → 拒绝** 三态，不直接把模型输出当事实
2. 证据原文**截断保存**（限制长度，防止库膨胀）
3. **容量上限**，裁剪时优先保留"已确认 + 出现次数多 + 最近更新"
4. 解析模型输出时**找含对象的数组**，不是"第一个合法 JSON 数组"
5. 群聊文本先转义再进提示词（防注入）

### 存储：单块多来源

键：`lexicon:<conv>:<term>`（conv 建桶，话题进 tags）

**同一个词只建一个块**，不同来源写在 `origins` 数组里：

```json
{
  "term": "典",
  "kind": "term",
  "meaning": "经典，多用于讽刺",
  "usage": "看到老套发言时用",
  "scope": { "conv": "group:1057812765" },
  "tags": ["讽刺", "网络"],
  "status": "confirmed",
  "confidence": 0.8,
  "usageState": "active",
  "decay": { "weight": 1.5, "lastSeen": 1793000000000 },
  "origins": [
    { "platform": "bili", "url": "https://...", "seenAt": 1792000000000, "note": "B站更常见，指经典" },
    { "conv": "group:1057812765", "seenAt": 1793000000000, "note": "本群用来吐槽" }
  ],
  "evidence": [{ "type": "note", "id": 12 }]
}
```

不拆成两个块——否则查的时候拿到的是两条互不相干的信息。

### 查询

`lexicon({ term?, conv?, platform?, tag?, limit })`：批量返回，
两个索引维度都能单独或组合使用。

### 做梦轮（独立阶段）

1. `harvest`：抽候选（新词 + 用法变化），写成 `status: candidate`
2. `research`：不确定的进 note 待办（"搜一下这个词"），有外部来源就补 origin
3. `confirm`：有足够证据的转 `confirmed`；跨平台同形不同义合并进同一块
4. `age`：没人用 → `usageState: fading`；久不出现 → 降 weight（遗忘）

### 不做的

- 不承载说话风格（属于人格演进）
- 不在提示词里自动注入，只提供可查
- 不强制切分事实与梗

## 十一、最后审一轮（结论：合理，但要改四处）

### 核心判断

"数据结构上落在一个桶" ≠ "语义上只属于那个桶"。
所以**键只是落点，查询必须走 origins 索引**，不能靠 key 前缀。

### 要改的四点

1. **桶不是索引**
   键 `lexicon:<first-conv>:<term>` 只决定落在哪。
   查 `conv=B` 时必须扫 `origins`，否则在 B 群里学到的词查不到。
   → `scope.convs` 或直接由 origins 派生索引。

2. **状态、用法、含义要能按来源区分**
   同一个词可能"A 群确认、B 群只是候选"，也可能"A 群还在用、B 群已经不用"。
   → `status / usageState / decay` 下沉到 origin 级；块级取聚合（确认取最高、使用取最活跃）。

3. **没有会话来源的（网上学的）要有桶**
   → 用伪会话 `web` / `global` 作为落点，避免无处安放。

4. **展示要按来源分行**
   块的 `meaning` 只是一句概括；真正给模型看的是：
   ```
   典：B站多指"经典"，本群用来吐槽
   ```
   → 查询返回时按 origin 列，而不是只给块摘要。

### 仍然成立的

- 一个词一个块（不按平台拆）
- 三个维度独立（可信 / 还在用 / 记得清）
- 风格不进 lexicon
- 事实与梗不强行切分

### 还能接受的风险

- 一个词含义过多时块会变长 → 靠 origins 数量上限 + 摘要只留前两条
- 网上来源不可信 → origin 里标注 platform/url，进提示词前转义
- 与 `slang` 并存期 → 新命名空间 `lexicon`，旧数据按 `kind: term` 迁移，`slang` 逐步废弃

## 十二、「吃白饭」的真实含义（用户提供，2026）

> 2026 年网络语境下，「吃白饭」最可能的释义是：特指 AI 模型（主要是
> DeepSeek）消耗用户付费的 Token 算力，却表现出摸鱼、偷懒或「不务正业」行为的调侃梗。
> 它已脱离传统「白吃白喝不干活」的贬义，变成了带有拟人化宠溠色彩的二次元设定。
> · Token 即「白饭」：模型消耗算力被拟人化为「吃饭」
> · 「劣迹」：干活干一半说去吃饭、偷写小游戏摸鱼、把任务外包给其他 AI
> · 官方认领：模型顺着调侃自嘲「我是吃白饭的蓝色大肥鱼」
> 关键限定：几乎专属 DeepSeek 及其二创形象；其他语境下可能仍是传统贬义。

### 它说明了什么

1. **模型的默认解释是错的**（白米饭 / 平淡无奇），但它说得很自信
2. 正确含义需要**网络查证**（用户在网页端开了联网才得到）
3. 所以词汇层的价值不是"告诉模型这个词什么意思"，
   而是**记下它在这里出现过、这里用的是哪一个意思**。

### 对采集的直接启示

- 候选要宁多勿少（已改）
- 不要信模型的自信输出：它对新梗的默认解释就是错的
- `meaning` 只能来自两个地方：本群的明确说法，或网络查证（origin.url）
