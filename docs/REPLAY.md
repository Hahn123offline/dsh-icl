# 真实输入与压力测试路线

闭环现在能证明“投递/gate/prompt/时间/focus 的契约”，不能证明“真实 QQ/B 站消息下当事人是否清楚、是否扛得住”。这份文档定义后者怎么测，**不需要先把 bot 扔进高流量群**。

## 1. 五天 QQ 记录有没有用

有用，但用途要分清：

- **有用于**：真实消息长度、语气、@/引用/图片比例、群聊与私聊比例、时间分布、人与人关系、lexicon 素材。
- **不足以**：证明高流量稳定性；五天记录不是压力源，也不是完整协议样本。
- **隐私**：只在本机做 fixture，去掉手机号、地址、token、可识别个人信息；不要提交到仓库。

把它做成 `fixtures/qq-5d.jsonl`，每行至少：

```json
{
  "ts": "2026-10-30T21:14:03+08:00",
  "source": "qq",
  "conversation": "group:123456",
  "conversationKind": "group",
  "sender": "u:10001",
  "senderName": "昵称",
  "messageId": "qq-...",
  "replyTo": null,
  "mentions": ["me"],
  "kind": "text",
  "text": "原文",
  "attachments": []
}
```

真实 connector 以后产出的也是这个形状：**fixture 和 live 共用同一个 message contract**，测试才不是另一套。

## 2. 不需要正式接 QQ 就能测的三层

| 层 | 输入 | 是否发消息 | 证明什么 |
|---|---|---|---|
| **Replay** | 五天记录 + 合成流量 | 否 | 消息形态、时序、focus/sleep/backlog、队列、去重、prompt 大小、恢复 |
| **Shadow** | 真实只读 connector | 否 | 真实来源、真实延迟、真实噪声；她只看不回 |
| **Canary** | 低流量群/白名单 | 是，限速 | 真实回复、真实当事人体验；小范围 |

现在只做 **Replay**。正式接入是 Shadow 阶段的事，而且先只读。

## 3. Seam 需要什么

真实 connector 必须提供，而不是让 ICL 猜：

- `messageId`：去重/幂等；
- `conversation` + `conversationKind`：群/私聊/频道；
- `sender` / `senderName`：谁；
- `ts`：真实时间，不是收到时间；
- `replyTo` / `mentions` / `attachments`：这条消息在回什么、是否点名、有没有图；
- `priority` 或可推导的紧急度（私聊/@/关键词）；
- 断线重连后的 **backfill/去重** 语义。

这些字段缺失时，当事人只能看到“一句话”，就会产生你看到的“模糊、不知道在回谁”。

## 4. 压力测试矩阵

不要只 replay 原速；原速五天可能还不如一次群聊爆发。

| 场景 | 目的 |
|---|---|
| 原速 replay | 信息形态、人格反应、当事人可读性 |
| ×10 / ×100 压缩时间 | 队列、批处理、prompt 增长 |
| 10 秒 100 条 burst | 手忙脚乱、focus 是否被打断 |
| 睡眠 30 分钟积压 500 条 | 醒来摘要是否有界、是否只挑重要 |
| 50 条重复/乱序 | 幂等、去重、旧消息是否重放 |
| 私聊 + 群聊 + @ 混合 | 优先级、focus 切换 |
| 模型延迟 30s + burst | 背压、是否丢消息、是否重复回复 |
| 重启/断线 | claim、raw、pending 恢复 |

每个场景都要有 **budget**：最大队列、最大 prompt token、p95 投递延迟、允许丢弃数、重复回复数。

## 5. 当事人视角的验收

不是“模型回了”，而是：

1. 她是否知道 **谁在哪儿说了什么**；
2. 她是否知道 **这条要不要回、先回谁**；
3. focus/sleep 后是否知道 **错过了什么、为什么现在看到**；
4. 醒来摘要是否 **有界、可行动**，而不是把 500 条倒进 prompt；
5. 她是否能说“我现在不回，因为……”，而不是被消息推着走；
6. 出问题时是否有 **可解释的状态**（积压多少、哪条被拦、为什么）。

建议每次 replay 产出 `transcript.md`：时间、来源、focus 状态、投递文本、她的回复/不回复、积压数。你按“如果我是她，我知不知道现在该干嘛”打分；这比断言更像真实体验。

## 6. 现在就能做的

1. 拿到五天记录的导出路径/格式，写 `tools/import-qq.mjs` 生成 fixture；
2. 写 `tools/replay.mjs`：读取 fixture，按虚拟时间投递，输出 metrics/report；
3. 先跑原速 + ×10 + burst 三组，不加真实 QQ；
4. 发现“当事人不清楚”的字段，再反推 connector 需要补什么；
5. 等 Shadow 只读稳定，再考虑 canary。

这样高流量群不是试验场，而是最后一步。
