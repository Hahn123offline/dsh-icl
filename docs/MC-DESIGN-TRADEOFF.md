# MC 设计分歧：模型控每个动作，还是 body 执行任务

> 这是本轮最重要的设计分歧，不能一句“快慢脑”带过。  
> 参考 `dsh-mc-agent` 的实际实现与文档，不复制代码。

## 1. 两种极端

### A. 工具型：模型直接控制每个具体动作

`dsh-mc-agent` 的路线：

- 40 个 `mc_*` 工具：连接、观察、移动、挖、放、合成、熔炼、箱子、战斗、交易、任务、看门狗；
- `mc_observe` 给第一人称截图 + 坐标/朝向/实体/背包；
- 长动作切成 ≤11 秒分片，返回进度；
- 自主层默认 `ai-led`：只监测 + 叫醒，不替 AI 吃/捡/穿/跟随；
- 行事准则明确写“你不是任务脚本，是这个世界的长期玩家”；
- 看门狗用 plugin-originated steer 注入，不伪造用户；
- 结果有 `confirmed/failed/unknown/stale`，不把“动作发出”当成功。

**得到：**

- 自然：模型自己看、自己走、自己挖，行为粒度接近玩家；
- 可适应：遇到地形、怪、聊天，能当场换策略；
- 第三方观感好：动作有停顿、观察、修正，不是“宏”；
- 表达能力完整：建造、战斗、交易、钓鱼都能组合。

**失去：**

- token/延迟：每步都要模型决策，观察图片和工具结果很贵；
- prompt/工具面复杂：40 个工具、长描述、参数多；
- 错误面大：每个动作都有自己的失败模式，需要大量 guard、超时、取消、重试；
- 模型容易“手忙脚乱”：小流量下也可能反复试错；
- 本地小模型很难稳定驾驭。

### B. 任务型：body 执行宏，模型只下目标

我们当前 `mc-body`：

- 6 个 `mcb_*` 工具：status/task/cancel/resume/events/say；
- 任务：mine/goto/patrol/explore/follow/chat/routine；
- body 做 pathfinder、挖、安全反射、重连、事件；
- 模型只决定“做什么”，不决定“每一步怎么走”。

**得到：**

- 低 token、低延迟：任务在 body 里跑，模型处理外部消息；
- 可预测/可测试：任务状态机、幂等、deadline、安全停止；
- 小模型友好：不需要 40 个工具；
- 长任务不阻塞会话；
- 安全边界清晰：body 可以拒绝/暂停危险动作。

**失去：**

- 自然度：body 的动作是宏，可能看起来机械；
- 现场适应：模型看不到“脚下这一格是什么”，任务中途地形变化只能靠事件；
- 表达力：建造/战斗/交易等复杂动作需要不断加任务类型；
- 归因：任务失败时，模型只看到“failed/stuck”，不知道具体哪一步；
- 第三方观感：如果 body 不设计停顿/观察/说话，容易像脚本。

## 2. 关键比较

| 维度 | 工具型 | 任务型 |
|---|---|---|
| 决策粒度 | 每个动作 | 每个目标 |
| token | 高 | 低 |
| 延迟 | 每步模型往返 | body 内连续执行 |
| 自然观感 | 高（模型现场反应） | 取决于 body 的“表演层” |
| 小模型 | 难 | 可行 |
| 安全 | 靠 guard/提示词 | body 硬约束 |
| 可测试 | 工具级、组合爆炸 | 任务级、状态机 |
| 复杂能力 | 40 工具组合 | 需加任务类型 |
| 失败归因 | 工具返回细 | 任务结果粗 |
| 长任务 | 切片、模型持续参与 | body 连续跑，模型可离开 |

## 3. 不是二选一：推荐“任务 + 窄具身工具”

保留任务抽象，但给模型 3–5 个**具身/社交**工具，而不是 40 个：

- `mcb_look`：看当前画面/射线/附近实体（或 `mcb_observe` 文本版）；
- `mcb_say`：说话（已有）；
- `mcb_stop`：立即停；
- `mcb_inspect`：检查某一格/背包/附近；
- 可选 `mcb_step`：短距离移动/让开，不替代 pathfinder。

这样：

- 90% 的体力活由 body 执行；
- 关键时刻模型能“亲自看一眼/说一句/让开”；
- 不把 40 个工具倒进 prompt；
- 失败时模型能补一次现场观察，而不是盲重试。

## 4. “自然第三方观感”到底靠什么

不是只有“模型控制每个动作”才自然。玩家看到的自然感来自：

1. **反应延迟**：不是瞬间完成，有停顿、观察、修正；
2. **社交时机**：有人说话时先回应/先停手；
3. **动作变化**：不是一直直线走/同一节奏挖；
4. **失败表现**：卡住会换路、受伤会退，而不是硬推；
5. **可解释**：她能说“我在挖木头，刚才卡了一下，换了个方向”。

这些可以由 **body 的表演层 + 事件摘要**提供，不必让模型控制每个 tick。  
工具型的优势是模型天然会做这些；任务型需要在 body 里显式设计，否则就像机器人。

## 5. 我们的选择

当前阶段：

- 保留任务型 body；
- 先补 `mcb_look` / `mcb_inspect` / `mcb_stop` 三个窄工具；
- routine 任务里加入“停顿/观察/换点”，避免机械重复；
- 用 transcript 评估第三方观感，而不是只看任务成功率；
- 本地模型优先任务型，因为 40 工具不现实。

如果以后发现：

- 社交场景需要大量现场微动作；
- 任务类型膨胀到 20+；
- transcript 显示“像脚本”；

再考虑把部分低层工具暴露给模型，或把 `dsh-mc-agent` 作为独立 actor 黑盒接入。

## 6. 数据收集

body 的 `routine` 任务应记录：

- collected / target / trips / eaten；
- mine error / move error / stuck；
- 位置变化、health/food；
- 任务耗时、失败原因；
- 事件 seq 与 taskId。

这些数据用于回答：

- 任务型是否真的更稳？
- 哪些失败是 body 的，哪些是模型目标选择？
- 自然观感差是“宏”造成的，还是缺社交反应？
