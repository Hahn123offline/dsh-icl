# 记忆 v3 报告：episode 形态与 episode 级评测（2026-11-12，进行中）

> 用户口径：episode 为主单位（不设数量/长度硬指标、没活不硬整）；typed 降级为块内注释；
> 重建后旧记忆归档。设计见 `docs/MEMORY-V3-DESIGN.md`。

## 1. 已落地

- `dream.memorySchema = 'v3'`：默认作业 wash → episodes → people → lexicon → consume → cleanup → index；
- `episodes` 作业：按经历窗口产出 episode（标题 + 完整第一人称正文 + 证据 + 人物 + 注释 + 关系），
  加一次**同日合并/改写轮**（只合并同一段经历/主题，保留全部细节；没有可合并就 []）；
- `episode` 命名空间（label 经历）纳入 recall，命中时返回**标题 + 完整正文**；
- cleanup 的块范围改为 episode/person/slang，合并时**并集证据/注释/关系**（v2 时合并会丢证据）；
- entity/relation 同步覆盖 episode（people→entities、relations→关系边、正文关系词兜底）；
- eval harness 新增 `--schema v3`：episode 级 formation 指标（块数/天、正文长度、证据覆盖、注释数）
  与 gold→episode 证据映射（多对一：一个 episode 可同时是多条 gold 的答案；person gold 同时挂
  person 档案与覆盖它的 episode，两种读路径都能命中）。

### 2.2 第 2 轮新增：内容完整性指标与完整性约束

- v3 formation 新增 `goldContentRate / contentCompletenessAvg`：不依赖期望映射，直接看每条 gold
  的内容词有多少出现在最好的一块 episode 正文里 → 防止"命中率靠筛掉难例"的幸存者偏差。
- 首测：focus 内容完整性 47–56%（v2 未测同口径），说明合并/概括确实会丢一部分细节；
  QQ 仅 30%（材料稀疏 + 原子 gold 很多），live 87.5%。
- 同步加了硬约束：
  - episode prompt 明确"当天每段值得留下的经历都要写进某一块，不要因为合并漏细节"；
  - 合并轮若模型给的正文比原文拼接短于 80%，直接回退为原文拼接（宁长勿丢）；
  - 解析器加"截断兜底"：模型输出被 token 上限截断时，逐个解析前面完整的对象，救回部分块，
    不再让整天 job 失败。

## 3. 当前结论与问题

- **成块形态达标**：块大、上下文完整、非配额化；focus gold 覆盖 84.4%（≥v2 formation R 81.3%），
  同一段经历自然合并（合并轮）；用户已确认形态"最接近理想记忆块"。
- **检索尚未证明优于 v2**：当前 v3 focus r5 81–82%（两次 fresh），v2 最新串行 r5 86–88%；
  第 1 轮的 93.6% 已确认含水分。v3 的剩余 miss 集中在"期望映射歧义 + 语义近邻排序"：
  - 同一段经历被拆/被合并后，一条 gold 可能横跨多块，期望映射只能取近似集合；
  - 关系/近邻块（舍友话题）容易互相挤占 top5。
- **本轮关键修复/新增**：
  - 内容完整性指标（gold 内容词覆盖率）与合并"宁长勿丢"约束；
  - 实体对扫描改为按内容词相关性只补 top3（去掉硬编码高分）；
  - 截断兜底解析（繁忙日不再整 job 失败）；episode 输出预算 7500。
- **仍需补的口径/质量项**：
  - QQ/live 需用当前代码重跑；QQ gold 覆盖/内容完整性偏低，要抽审是"没写进去"还是"换说法没匹配"；
  - 三源重复采样方差（本轮 focus 两次 fresh：r5 82.1 / 81.0，已比首轮 93.6/71.4 稳定）；
  - 需要 episode 专用检索方案（LLM rerank top-k，或用内容词+标题的混合打分）才能超过 v2。

### 2.3 第 3 轮：检索上限诊断（LLM 重排实验 + 候选扩召回）

- **上限实验**：把全部 30 个 episode 标题+正文开头直接给云端模型选 1–3 块（每 probe 一次调用），
  focus 14 个有期望 probe 上 **hit@5 = 92.9%**（当前 recall 同 run r5 67.9%）→ **差距主要在
  "候选生成/排序"，不在 episode 内容本身**；LLM 重排能把上限拉到 ~93%，但每轮召回加一次模型调用
  成本/延迟不可接受（生产不应默认这么干）。
- 已做（低成本、不调模型）：
  - episode 单独放宽一轮候选（粗块 embedding 相似度普遍低于原子块，严格 floor 会把正确块直接筛掉）；
  - person gold 同时挂 person 档案与覆盖其证据的 episode（修复 recall 探针永远不可能命中的映射 bug）；
  - 内容词增加 3 位以上数字与更高权重（端口号/群号类 queries）；
  - 期望映射最多 3 个 episode（多对一），减少"一块 gold 被拆到多块"的映射歧义。
- 当前 focus v3（同一 formation 上重排）：r2/r3/r4 三次样本 r5 = 77.4 / 90.5 / 74.3%，miss 7–14%；
  **方差仍大，尚未稳定超过 v2（86–88%）**。
- 下一轮优先方案：**episode 正文分段索引**（正文按 ~250 字切段、每段单独向量索引，命中段回映射到
  整个 episode）——用便宜方式获得"细粒度匹配 + 粗粒度返回"，目标把候选召回率拉到 LLM 重排上限附近，
  再决定是否保留 LLM rerank 作为可选项。

## 4. 下一步（本目标内）

1. **episode 检索专用方案 A/B**：先用离线 rerank 实验（云端一次/查询，top10 选 1–3 块）验证上限，
   再把可提取的规则蒸馏进 recall（不每轮加 LLM 调用）；
2. 期望映射口径修正：gold 覆盖多块时按"内容词覆盖率"给期望集排序/限定，减少映射歧义；
3. QQ/live 用当前代码重跑 + 内容完整性抽审；
4. 重建 runner（raw → v3 逐天幂等、可中断、旧库归档）在 lab 三源跑通；
5. 三源稳定后出 live 重建 dry-run 清单，停下等用户确认。
